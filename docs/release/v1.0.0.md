# pass-lang v1.0.0 — stable

**1.0.** The public API is frozen and stable. v0.1.0 stood up the scaffold and the
quality gates; v0.2.0 built the core — the `Pass` plugin-seam trait, the
`PassManager` pipeline with fixpoint iteration, and the run `Report`. This release
ratifies that surface as the `1.0` contract: it follows Semantic Versioning,
carries no breaking changes before `2.0`, and ships with the full property-test and
benchmark suite verified on Linux, macOS, and Windows.

There is no breaking change from `0.2.0` — a `0.2.0` program compiles and behaves
identically. The freeze adds only what hardens the release: a pre-sized run report,
`#[inline]` on the hot-path methods, a third runnable example, and the stability
documentation.

## What is pass-lang?

The pass manager: it orders optimization and transform passes and runs them over a
unit of compilation, and it is the plugin seam capability crates register their
passes into. It is generic over the unit a pass rewrites — an intermediate
representation, a single function, a module, an abstract syntax tree, or a struct
bundling an IR with the diagnostics and analysis a pass needs. A consumer brings
the unit, implements one trait per transform, and runs the pipeline; the manager
schedules and runs, and never inspects the unit itself. It is self-contained — no
first-party dependency — the same shape as LLVM's pass manager (generic over
Module / Function / Loop) or Cranelift's pass pipeline.

```rust
use pass_lang::{Outcome, Pass, PassError, PassManager};

struct DropZeros;
impl Pass<Vec<i64>> for DropZeros {
    fn name(&self) -> &'static str { "drop-zeros" }
    fn run(&mut self, unit: &mut Vec<i64>) -> Result<Outcome, PassError> {
        let before = unit.len();
        unit.retain(|&x| x != 0);
        Ok(Outcome::from_changed(unit.len() != before))
    }
}

let mut pm = PassManager::new();
pm.add(DropZeros);

let mut unit = vec![0, 1, 0, 2, 3];
let report = pm.run(&mut unit).unwrap();
assert_eq!(unit, vec![1, 2, 3]);
assert_eq!(report.changes(), 1);
```

## The 1.0 surface

The frozen contract is the pass manager core:

- **The seam** — the `Pass<T>` trait (`name` + `run`) and the `Outcome`
  (`Changed` / `Unchanged`) it reports.
- **The pipeline** — `PassManager<T>`: `new`, `add` (registration, the plugin
  seam), `len` / `is_empty`, `run` (one sweep), and `run_to_fixpoint` (repeat to a
  fixpoint under a bound that guarantees termination). Implements `Default`.
- **The report** — `Report` and `PassRun`: `runs`, `changes`, `iterations`, and
  `converged`.
- **Failure** — `PassError`: the failing pass's name and a reason, with `Display`
  and `core::error::Error`.
- **Serialization** — `serde` derives `Serialize` for the reporting types under the
  `serde` feature.

`Outcome` is a deliberately complete two-variant enum. The structs keep their
fields private, so new methods or fields stay additive within `1.x`.

## SemVer promise

The crate follows [Semantic Versioning](https://semver.org):

- No documented item is removed or changed in a breaking way within `1.x`; breaking
  changes wait for `2.0`.
- New functionality is additive and arrives in minor releases. The `Pass` trait
  will not gain a required method within `1.x`; any new method ships with a default
  body.
- The MSRV is Rust `1.85`; raising it is a minor change, never a patch.
- Behaviour is part of the contract: passes run in registration order;
  `run_to_fixpoint` always terminates within its bound; a pass failure halts the
  pipeline and names the failing pass.

The full statement lives in [`docs/API.md`](https://github.com/jamesgober/pass-lang/blob/main/docs/API.md#semver-promise).

## Breaking changes

**None.** `1.0.0` makes no breaking change to the `0.2.0` surface.

## Hardening since 0.2.0

- **A pre-sized report.** `run` and `run_to_fixpoint` size the report's run list to
  the pass count up front, so a sweep records its outcomes without reallocating.
- **Inlined hot path.** The methods called once per pass per sweep — `Outcome`'s
  accessors, `PassRun`'s accessors, and the `Report` readers — are `#[inline]`. The
  manager's per-pass cost stays a single indirect call into the pass.
- **A third example.** `contextual_passes` shows the pattern where the unit bundles
  the program with a diagnostics log, so passes share context without a global.

The manager is held to the invariants in `dev/DIRECTIVES.md` by property tests:
determinism (the same pipeline over the same input yields the same result),
fixpoint termination (`run_to_fixpoint` never exceeds its bound), fixpoint
stability (a reported convergence survives a further sweep), and report accounting
(every pass that ran is recorded). Benchmarks confirm the freeze introduced no
regression.

## Verification

Run on Windows x86_64 and Linux x86_64 (WSL2 Ubuntu), Rust stable 1.95 and the 1.85
MSRV; the same commands run across the CI matrix on Linux, macOS, and Windows:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo test
cargo test --all-features
cargo build --no-default-features
cargo +1.85 build --all-features
cargo build --examples
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo deny check
cargo audit
```

All green. Counts at this tag: 27 unit + 4 integration + 3 property (`proptest`) +
38 doctests, plus 2 `serde` serialization tests with `--all-features`. The doctests
include every `rust` example in `README.md` and `docs/API.md`. Three runnable
examples: `cargo run --example expr_optimizer`, `text_normalizer`, and
`contextual_passes`. Benchmark baselines (release, WSL2 Ubuntu): a three-pass sweep
over a one-thousand-element unit ~1.0 µs; a 33-sweep fixpoint over 256 elements
~2.0 µs.

## What's next

The `1.0` surface is stable until `2.0`. Future work is documentation, tests, and
internal optimisation that does not change the public contract — plus the additive
candidates the design leaves room for: analysis passes with cached, invalidatable
results, and inter-pass dependency declaration, each a minor release when it lands.
